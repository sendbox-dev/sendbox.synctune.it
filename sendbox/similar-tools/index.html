Choosing an agent sandbox

On this page

  1. Options and tradeoffs
  2. Distinctive SendBox built-ins
  3. When SendBox is a good fit
  4. Questions to ask before choosing
  5. Sources

The right sandbox depends on what you need to isolate and who should operate it. A reproducible development environment, an interactive agent session, and an API that executes code for many users solve related but different problems.

SendBox focuses on CLI agent sessions on a Mac or Linux host you control, with a VM boundary and a reviewable policy for workspace access, entry commands, network destinations, credentials, and MCP tools.

These are workflow comparisons, not a security ranking or a feature-parity claim. Local and hosted variants can have different boundaries. Product capabilities change; verify the current documentation for your chosen deployment rather than relying on a product name alone.

Distinctive SendBox built-ins

These two workflows distinguish SendBox's integrated CLI stack in the reviewed sources. This is a comparison of documented built-ins, not proof that another project cannot provide equivalent behavior. An undocumented capability is unknown, not unsupported.

WorkflowWhat SendBox implementsRelated capabilities and limits
Pre-delivery npm package gateA trusted registry proxy quarantines tarballs, verifies package identity and integrity, enforces configured signature/provenance requirements, and inspects archive content without executing package code. Only an allow verdict releases bytes to the workload. Exceptions bind to an exact artifact digest.The reviewed alternative sources do not establish an equivalent built-in tarball pipeline. Chainguard's product page advertises lockfile verification; that should not be equated with SendBox's static archive inspection. Generic registry access controls or installing a scanner inside a sandbox are also different boundaries.
Post-session GitHub Safe OutputsA native partial-conformance gateway records bounded GitHub requests with session/policy provenance. After guest teardown, the host verifies the batch and either persists a preview or applies permitted writes with a host-only token.This is an integration of the GitHub Agentic Workflows design, not an invention of SendBox. Docker Sandboxes is also a supported runtime for GitHub Agentic Workflows, where a separate Safe Outputs job performs writes. That is a documented alternative when CI orchestration, rather than a local CLI integration, fits your workflow.

Both controls are disabled by default and supported on Apple/Kata persistent sessions only. Package inspection is npm-only; other package adapters are not implemented. Signature/provenance checks default to verifying evidence when present; use required to reject its absence. Static inspection is not proof that a package is safe. See the package guide.

Safe Outputs defaults to staged mode when enabled and supports only a subset of GitHub.com operations. Apply mode prevalidates the batch but performs remote writes sequentially, so a later API failure can leave earlier writes applied. See the gateway architecture and limitations.

VM isolation, network policies, external credential injection, MCP support, snapshots, and audit records are not claimed as SendBox-only features. Agent Substrate, Chainguard, Docker, and other tools provide overlapping controls. Some alternatives also offer capabilities SendBox does not: cluster scheduling, managed compute, durable full-VM resume, Windows environments, or an embedded sandbox SDK.

When SendBox is a good fit

Choose SendBox when you want to keep using terminal agents on infrastructure you manage, avoid granting them broad access to your host environment, and review their permissions in one configuration.

It is especially relevant when you need the combination of a VM boundary, explicit model-provider egress, per-server MCP tool rules, registry inspection, and GitHub workflows without tying the session to one coding agent.

Choose a different approach when your primary need is a managed execution API, large-scale environment scheduling, or simply a shared development setup. A cloud sandbox platform can own more infrastructure for you; a devcontainer may be sufficient when reproducibility, rather than containing untrusted code, is the main goal.

Questions to ask before choosing

  1. What is outside the boundary? Does the workload share a kernel with the host or other workloads? Which host files, runtime sockets, and MCP servers remain reachable?
  2. What can leave the environment? Are outbound destinations restricted, and what happens when an agent or plugin ignores proxy settings?
  3. Where do credentials live? Can the agent read them, or does a trusted service inject them only for approved upstream requests?
  4. How do changes reach your repository? Is the workspace shared read/write, copied, or synchronized? What must you review before running changed files?
  5. What does failure look like? Do missing controls stop execution? What evidence, cleanup, and rollback are available?
  6. Who operates it? Who patches the runtime, verifies artifacts, provisions compute, and handles concurrency and tenant separation?

For SendBox, the shared workspace is writable, workload secrets are accessible to the workload, and command policy does not recursively authorize descendant argv. See security expectations and the security model before treating any control as a guarantee.
