Install SendBox through Homebrew or a verified release artifact, or build the host binary from source when developing the project.

Requirements

Choose a runtime before installing. Apple and Kata support interactive and headless agent sessions; Hyperlight is an explicit one-shot provider with a narrower capability set.

Workload image versus guest bundle

Persistent agent sessions need both:

  • A digest-pinned Linux workload image for the guest architecture, containing your agent, its runtime dependencies, certificates, shell, and development tools.
  • A verified signed guest bundle and trust root, containing SendBox's security services. These do not install the agent or its development tools.

Apple and Kata workload images must also provide the nft executable and its shared-library dependencies. Mandatory egress enforcement requires a writable cgroup v2 root, delegated memory/PID controllers, CAP_NET_ADMIN, SO_MARK, and kernel support for nftables socket cgroupv2. A plain Alpine image without nftables is not sufficient, even when the network policy denies all traffic. Missing enforcement prerequisites are errors, not grounds to skip hardening.

The execution broker resolves entrypoint and working-directory paths without following symlinks. Use a regular executable path and match that exact argv in the command policy. Alpine's default /bin/sh is a BusyBox symlink; a workload image using that entrypoint must materialize a regular shell executable or select another regular entrypoint with the corresponding policy. Do not disable descriptor-resolution checks to accommodate an image.

The production guest image is intentionally minimal: it contains no Python, Node.js, compiler, bpftrace, or development headers. Keep bundle executables, metadata, and trust roots in the root-owned locations described below. A public key shipped beside a bundle is not self-authenticating; verify release provenance before trusting it.

Homebrew

The existing mbianchidev/tap uses a formula, not a GUI cask.

Before installing, check the dependency security status. The v0.2.3 TLS-fix floor is necessary but no longer sufficient. Published v0.2.2 and earlier binaries predate RUSTSEC-2026-0382 and RUSTSEC-2026-0383. Published binaries cannot inherit source fixes. The planned central updater keeps this patched-release floor and verifies the artifacts before updating the formula. Central automation is pending review and activation in the tap; see stable Homebrew updates. This source change does not publish a replacement release or activate that automation.

Dependency security status

The November 11, 2026 CI audit identified additional advisories in the unchanged v0.2.5 source/release lockfile. Source now requires at least cap-std/cap-primitives 4.0.3, hickory-proto 0.26.2, and rustix 1.1.6; the lockfiles resolve hickory-proto 0.26.3:

  • RUSTSEC-2026-0482: capability filesystem sandbox escape, fixed by cap-primitives 4.0.3.
  • RUSTSEC-2026-0491, 0487, 0488, 0490, and 0489: DNS allocation/panic defects fixed by hickory-proto 0.26.2.
  • RUSTSEC-2026-0486: an extended-attribute buffer unsoundness warning fixed by rustix 1.1.6.

These are source fixes, not newly published artifacts. Rebuild and independently review both the host and signed guest bundle in a new release; an installed v0.2.5 binary or guest bundle does not inherit dependency updates or Apple 1.7.1 compatibility. Do not treat an older release as patched merely because it passes signature/digest verification or the historical TLS version floor.

Formula installation

Install with:

brew install mbianchidev/tap/sendbox
sendbox --version
sendbox --help

It reuses verified published host archives for macOS arm64, Linux x86_64, and Linux aarch64. There is no frontend build, background service, or automatic runtime installation. Intel Macs are not supported. The Apple runtime still requires macOS 26+, Apple silicon, and the pinned container CLI; Linux needs the Kata/KVM runtime described above.

The binary is linked into Homebrew's bin; the complete release payload, including setup.sh, configuration examples, and signed guest assets, lives under $(brew --prefix mbianchidev/tap/sendbox)/libexec.

Stage the guest bundle

Homebrew's Cellar is user-owned. Do not pass the Cellar's guest bundle or public key directly to sendbox run, change Cellar ownership, or run Homebrew with sudo. SendBox deliberately requires root-owned runtime artifacts and trusted ancestors. A formula install does not weaken that requirement.

Before trusting the embedded guest key, independently verify the original archive's provenance:

brew fetch --formula mbianchidev/tap/sendbox
gh attestation verify "$(brew --cache --formula mbianchidev/tap/sendbox)" \
  --repo mbianchidev/sendbox \
  --signer-workflow mbianchidev/sendbox/.github/workflows/release.yaml

Copy the matching payload to a new, versioned, root-owned location. The following commands are an explicit administrator step, not a formula hook. Stop if the destination already exists and inspect it instead of overwriting an existing runtime installation:

prefix="$(brew --prefix mbianchidev/tap/sendbox)"
version="$(sendbox --version | awk '{print $2}')"
case "$(uname -m)" in
  arm64|aarch64) architecture=aarch64 ;;
  x86_64) architecture=x86_64 ;;
  *) printf 'Unsupported architecture\n' >&2; exit 1 ;;
esac
GUEST_DIR="/opt/sendbox/$version/guest/$architecture"
test ! -e "/opt/sendbox/$version" || {
  printf 'Guest destination already exists; inspect it before continuing\n' >&2
  exit 1
}
sudo install -d -o 0 -g 0 -m 0755 /opt/sendbox "$GUEST_DIR"
sudo cp -R "$prefix/libexec/guest/$architecture/bundle" \
  "$prefix/libexec/guest/$architecture/release-public.key" "$GUEST_DIR/"
sudo chown -R 0:0 "/opt/sendbox/$version"
sudo find "/opt/sendbox/$version" -type d -exec chmod 0755 {} +
sudo find "/opt/sendbox/$version" -type f -exec chmod 0444 {} +
sudo find "$GUEST_DIR/bundle/bin" -type f -exec chmod 0555 {} +

Ensure /opt and /opt/sendbox are real root-owned directories, not symlinks, and are not group/world writable. Launch the CLI as your normal user, with --bundle "$GUEST_DIR/bundle" and --trust-root "$GUEST_DIR/release-public.key". Configure the runtime separately using the Apple or Kata guide.

Upgrade and removal

brew update
brew upgrade mbianchidev/tap/sendbox
brew uninstall mbianchidev/tap/sendbox

After upgrading, verify and stage the new version's guest bundle before using it with the new CLI. Keep old root-owned bundles until no sessions need them; they are outside the Cellar and are not removed by Homebrew.

Upgrades and removal preserve project .sendbox.yaml files, workspace contents, user state under ~/.sendbox, and macOS Keychain credentials. No uninstall or cleanup hook deletes these locations. Remove retained state and versioned /opt/sendbox payloads separately only when you intentionally want to erase them. Do not mix a manual /usr/local/bin/sendbox install with Homebrew or use brew link --overwrite; inspect and migrate the old installation explicitly.

Release artifacts

Download the matching artifact from Releases:

HostArtifacts
macOS arm64tarball, unsigned .pkg, unsigned .dmg
Linux x86_64tarball
Linux aarch64tarball

Each host archive and macOS installer contains the production sendbox binary, configuration examples, setup helper, and matching signed guest bundle. The release also publishes standalone guest-bundle archives.

Verify GitHub provenance before trusting the embedded guest public key, then verify the adjacent checksum:

gh attestation verify sendbox-<version>-<platform>.tar.gz \
  -R mbianchidev/sendbox
shasum -a 256 -c sendbox-<version>-<platform>.tar.gz.sha256

Install a verified tarball into a root-owned runtime location:

sudo tar xzf sendbox-<version>-<platform>.tar.gz -C /opt
sudo install -m 0755 /opt/sendbox-<version>-<platform>/sendbox \
  /usr/local/bin/sendbox

Or install the verified macOS package:

sudo installer -pkg sendbox-<version>-macos-arm64.pkg -target /

Run /opt/sendbox-<version>-<platform>/setup.sh as your normal user after installing a tarball. The root-owned extraction preserves the runtime trust boundary for the bundled guest artifacts; do not copy them into a user-writable directory before launch.

Production guest bundles provide static-musl guest and execution binaries, strict CO-RE BPF objects, signed manifests, inventory, SBOM metadata, deterministic rootfs tarballs, and minimal scratch OCI images for Linux x86_64 and arm64. See guest artifact bundles for details.

Publishing a release

Releases are triggered by pushing a vX.Y.Z tag, not by make release, which only builds locally. From a clean checkout with origin pointing to mbianchidev/sendbox, run:

./scripts/release.sh 0.2.0

The script requires Bash, Git, Python 3.11 or newer, and an authenticated GitHub CLI account with permission to push branches and tags, merge PRs, and rerun Actions workflows. Cargo is also required when preparing a new version bump. For a new release, pass a stable X.Y.Z version greater than the version on main; a leading v is also accepted.

Git and GitHub CLI pagers are disabled for the script and its subprocesses, so output never pauses for pager input and the script exits on its own after printing the release URL.

After its preflight safety checks, the script switches the invoking checkout to main and pulls origin/main with --ff-only before inspecting or resuming a release. A failed pull or divergent local main stops the script before any release operations. If main is checked out in another Git worktree, run from that checkout instead; the script never forces a second checkout of main.

For a new release, it creates an isolated worktree from updated origin/main, updates [workspace.package].version and the CLI version assertion, and refreshes every committed Cargo lockfile, including standalone fuzz, spike, and qualification workspaces. Unrelated dependencies are not upgraded.

It then opens a version-bump PR, waits for CI checks to pass, and merges without bypassing branch protections. An annotated tag is pushed at the PR's merged main commit, after verifying that its Cargo version matches the tag. The invoking checkout stays on main at its startup pull, while the original feature branch is unchanged and version edits remain in the isolated worktree.

The script watches the Release workflow, which publishes GitHub assets and GHCR artifacts, including macOS installers, Linux archives, and signed guest bundles. The required release-signing secret is already configured; no local signing key is needed.

Native macOS arm64 and Linux x86_64/aarch64 CLI tests and builds run in parallel with the signed guest builds. Each packaging job waits for both producers and verifies the checksum and executable mode of its matching, commit-specific CLI archive before combining those exact tested bytes with the signed guest payload. The internal CLI archives retain the default Actions artifact lifetime and are excluded from published assets. Signing, clean guest builds, package checksums, release provenance, and GHCR publication are unchanged. Homebrew verification and formula updates are owned by the tap, as described below.

Generic build and packaging hosts follow ubuntu-latest and macos-latest where compatible. Linux CLI producers retain Ubuntu 24.04 to avoid raising their glibc baseline when the alias advances; native arm64 jobs retain ubuntu-24.04-arm because no supported floating arm64 Ubuntu alias exists. The macOS producer pins and verifies the existing arm64 binary deployment floor at macOS 11.0 independently of the build image. The Apple runtime still requires macOS 26 or newer.

On failure, the script stops and preserves any branch, PR, or tag already created. Resolve the underlying failure, then run the same command with the same version to resume. It reuses a committed release/vX.Y.Z branch and its open or merged version-bump PR rather than creating duplicates. Uncommitted release files are retained in the temporary worktree whose path is printed for recovery; inspect and finish that work before retrying.

If the tag already exists, the script verifies its Cargo version and ancestry on origin/main, then watches its existing Release workflow. Failed runs rerun only failed jobs and their dependents, retaining successful build outputs. Cancelled or otherwise unsuccessful completed runs restart the whole workflow. The script waits for the new attempt before watching it; active runs are only watched, and successful runs are not restarted. Retries remain subject to GitHub's rerun window and artifact retention.

Reruns use the original tag's commit and workflow definition, not newer changes on main. If a fix changes source or workflow code, publish a new version from the fixed commit. Recovering a failed, unpublished tag instead requires an explicit maintainer decision outside this script; never move a published tag.

A local tag not yet pushed is published unchanged. Existing tags are never replaced, and conflicting local and remote tags or release branches require manual inspection. Check registration, merge completion, release run discovery, and retry registration each have a ten-minute timeout.

Stable Homebrew updates

Homebrew updates are owned by mbianchidev/homebrew-tap, not the SendBox Release workflow. SendBox continues to publish its host archives, signed guest bundles, adjacent SHA-256 files, and tag-bound release-workflow attestations. It does not push tap branches or create tap PRs, and requires no tap-write secret, cross-repository token, or new credential.

The central updater is pending review and activation in the tap. Once enabled, it checks included projects' stable releases hourly and downloads the existing SendBox archives for macOS arm64, Linux x86_64, and Linux aarch64, plus their checksum files. It recomputes SHA-256 against GitHub's asset digests and the adjacent published checksums, and verifies attestations from mbianchidev/sendbox/.github/workflows/release.yaml bound to refs/tags/vX.Y.Z on GitHub-hosted runners. It does not rebuild the CLI or guest bundles.

Only a published, non-draft, non-prerelease vX.Y.Z matching GitHub's latest stable release at or above the patched-release floor v0.2.3 is eligible. Older releases, a newer formula, and a stable release that supersedes an in-flight verification cannot downgrade it. Prereleases do not update the stable formula, GitHub's latest release, or the GHCR latest tag.

The tap prepares one verified release-only batch PR and explicitly runs its complete native CI. A separate trusted-default-branch workflow automatically merges eligible release-only bot updates only after CI and review guards pass. Updates normally become available within an hour of artifact publication, subject to those gates. Implementation PRs still require human review and merge; source changes alone do not enable central automation.

After the source and tap implementation PRs are approved and merged and the central updater is enabled, revoke the retired SendBox tap SSH deploy key and remove its old Actions secret. Older tag reruns retain their original workflow definition; retiring that credential prevents them from writing to the tap. Keep the release-signing secret configured.

If an update is blocked, inspect the central updater's Actions run and update PR in the tap, resolve the verification, CI, or review failure, then rerun the applicable tap workflow. Do not run scripts/release.sh, create another tag, move an existing tag, or republish artifacts just to retry a formula update.

Build from source

git clone https://github.com/mbianchidev/sendbox.git
cd sendbox
make install

Source installs require a separately attested signed guest bundle and trust root; tagged host artifacts already include the matching pair.

For an interactive runtime preflight and configuration flow:

./setup.sh

Kata installation and containerd configuration are documented in the Kata Containers guide.

Unsigned macOS packages

The .pkg and .dmg are not Apple-signed or notarized. Verify their GitHub attestation and checksum before installation. If Gatekeeper blocks a verified download, approve that artifact in Finder or System Settings, or remove only its quarantine attribute:

xattr -dr com.apple.quarantine sendbox-<version>-macos-arm64.pkg

Do not disable Gatekeeper globally. The package removes quarantine from the installed /usr/local/bin/sendbox only after the installer has been approved. The DMG install.sh replaces the shared payload through a fresh staging directory, removes stale upgrade files, and enforces root ownership with 0555 guest executables and 0444 bundle metadata and trust roots.

Continue with the configuration guide after installation.
